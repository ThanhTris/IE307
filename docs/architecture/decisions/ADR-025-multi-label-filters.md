# ADR-025 — Multi-label dish data for the preference filters

- Status: **Accepted by the project owner in chat on 2026-11-13** (to be re-confirmed by Trí in review).
- Scope: canonical B-supplement runtime (as ADR-024) and the data contract of the next catalogue dataset.
- Runtime: `0051_multi_label_filters.sql` (schema 0.27.0), applied to the local QA database only.
- Builds on: ADR-024 (soft preference ranking, 5–20 dishes).

## Context

A dish is used flexibly: rice is eaten at breakfast, lunch and dinner; bún chả is both noodles and grilled; a dish can be
spicy and fatty; hủ tiếu is common in the South and the Mekong Delta. ADR-024 modelled region as one `origin` value and
Béo / Ngậy as a tag inside `categoryIds`, and placed the new group IDs in the app with ad-hoc UUIDs that did not follow the
catalogue pipeline's ID rule.

## Decision

1. **Every filter takes many values per dish.** `mealSlots`, `categoryIds` (families), `cuisineIds` (regions) and
   `flavor` kinds are all multi-valued, and a match on **any** value counts (once per member per dimension).
2. **Regions are cuisines.** Four cuisine codes `vi_north`, `vi_central`, `vi_south`, `vi_west`; a dish carries several in
   `cuisineIds`. The legacy single `origin` keeps counting, mapped to the same region, but is not filled for new data.
3. **Béo / Ngậy is the fifth flavour**, `flavor.fatty` (present + intensity), optional next to the four classic kinds.
   The tag in `categoryIds` is removed.
4. **One source for IDs and groups.** `data-preparation/config/filter_taxonomy_v2.json`, generated by
   `data-preparation/scripts/filter_taxonomy.py`, holds the new family and region codes, which families make up each
   screen group and the IDs (`stable_id`, identical to the catalogue pipeline). The app file
   `filterGroups.generated.ts` is generated from it; Python tests check both are current. `taxonomy_v1.json`, bundle
   1.1.0 and its manifest are unchanged.
5. **Server.** `valid_preferences` (baseline helper and GM-06 history) accepts optional `fatty` and still rejects unknown
   kinds; `preference_match` uses any-shared family / region and the fifth flavour; stored results drop `origin` and
   `flavor.fatty` (`canonical_card`) so the GM-06 card shape is unchanged.
6. **Missing data stays neutral.** A dish without `mealSlots` is never drawn; missing family, region or flavour data
   earns no points and costs none. Nothing is guessed.

## Consequences

- The data team fills several values per dish with a source for each (task #170); validation is
  `filter_taxonomy.py --validate`.
- The dataset schema `dish-catalogue-v1` allows four flavours and the v1 codes; the next dataset (1.2.0) must extend it
  for `fatty` and the new family and region codes. Not done here because the GM-40 manifest pins the current files.
- The real catalogue loaded on QA is the basic projection (no `flavor`), so ranking by flavour is covered by SQL tests
  with synthetic cards, not by an end-to-end run on real data yet.
- Not run: SQL/domain parity CI (`scripts/dish_v4_ci.py`, `scripts/gm20_canonical_check.py`).
